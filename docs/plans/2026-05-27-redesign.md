# /snoop categorical redesign
Date: 2026-05-27 Status: Draft for review Lineage: extracted from a deep dive on `mvanhorn/last30days-skill` and applied to `~/.claude/skills/snoop/`
## Thesis in one line
Stop guessing strings. Start resolving people. Pattern generation becomes the fallback, not the engine.
## Post-dual-voice-review changes (2026-05-27, post-c6)
Folded from Codex + Claude subagent reviews. Both bottom-lined "ship with changes," not "ship as-is" or "rewrite." Key shifts:

- **Score is split into 3 fields** (`belongs_to_person`, `current_work_address`, `deliverable`), each 0-1 with abstention. The single-decimal `score` was a fake probability; reviewers were right.
  
- **Ambiguity has 3 explicit states** (`single_plausible_match`, `multiple_plausible_matches`, `insufficient_identity_evidence`). `unique` was a false-confidence trap (single-candidate ≠ unique).
  
- **Plan-provided handles are untrusted hints** until independently bound by 2 anchors (name + company-domain match, or repo ownership, or profile cross-link). Defends against "evidence laundering" via hallucinated handles.
  
- **P1 scope is cut.** Defer `hn_profile`, `package_registry`, `x_bio`, `pgp_keyserver`, `linkedin_cookies` to P2/P3. P1 source set: `git_emails`, `gh_profile`, `personal_site` (mailto: anchors only), `pattern_gen`, `verify_smtp` (refactored). Plus plumbing: `normalize`, `score`, `render`, `diagnose`, `person_resolve`.
  
- **New** `lib/normalize.py` for Unicode/ASCII-fold, name-variant generation, IDNA. Pre-existing schema layer had zero normalization. Subagent finding F2.
  
- **Per-resolver 5s timeout** via `future.result(timeout=5)`. Slow `personal_site` or `whois` shouldn't stall the whole call.
  
- **Output becomes a contact decision card**, not a "person card." Per Codex finding #2: best business channel + reason to trust + reason to avoid + next action.
  
- **§Calibration is a real section.** Labeled fixture of 5-10 real targets ships with P1; expand to 25-30 post-P1. Replace estimated hit rates with measured numbers in SKILL.md.
  
- **§Test architecture is a real section.** VCR-mocked per-resolver tests + `pytest -m network` for live tier.
  
- `cache.db` **chmod 600; no lookup log by default.** Local security posture per Codex #11.
  
- **§Counter-thesis acknowledges the Hunter/Apollo waterfall alternative.** /snoop's bet is small-N + explainability + free, not high-volume CRM enrichment.
  

Deferred to v2 (won't block P1 ship): source-family clustering for over-counted independence (Codex #8); full company-domain resolution subsystem (Codex #10); `personal_site` regex extraction + Cloudflare deobfuscation (Subagent F7); 14-module → 3-group refactor (Subagent F11).

## The reframe
`mvanhorn/last30days-skill`'s central architectural insight is _resolve the entity before searching_. Given "OpenClaw" it figures out `@steipete` + `steipete` on GitHub + `r/openclaw` _before any retrieval fires_. Pattern-against-keyword-space happens after it knows what it's looking at.

Applied here: a person already has emails. They are on public git commits, in WHOIS records, on PGP keyservers, on conference speaker pages, in npm publisher metadata, on their own blog footers. `/snoop` never looks. It jumps straight to permuting strings.

The categorical move: turn `/snoop` into a person-resolver that fans out across {==~5 free public sources==}{>>are there more that last30days does that we can / should also use here?<<}{id="c2" by="user" at="2026-05-27T17:29:30.728Z"}{>>Yes — being too conservative in v1. Going back through last30days's 17-source list and the broader "public-leak" surface, the high-yield additions are: (1) **GitHub profile email + bio + profile-README** (distinct from commit emails; ~25-35% hit rate on devs, trivial to add — promoting to P1), (2) **Hacker News public profile** (`news.ycombinator.com/user?id={h}` has a public email field, ~40% hit rate on YC/tech-founder targets, near-zero outside that population — P1 for that audience), (3) **personal-site scrape** (covered by c3 — P2), (4) **npm/PyPI publisher email** (near-100% precision on registered publishers, narrow audience — P2), (5) **X bio regex** (cheap if we already have X auth via Bird cookies — P2/P3). Lower-yield long-tail: Substack, Bluesky bio, Mastodon profile fields, conference speaker pages, podcast guest pages — all P3. Updated the architecture, schema, scorer, and ranked task list to reflect this. Output is a person card with `(address, confidence, provenance, last-verified)` rows, split into Work and Personal, with channel-alternative hints when email confidence is uniformly low.

### Schema
```python
@dataclass(frozen=True)
class Source:
    type: Literal["git_commit", "gh_profile", "gh_readme", "hn_profile",
                  "whois", "personal_site", "substack", "package_registry",
                  "x_bio", "pgp", "linkedin", "pattern", "smtp",
                  "manual_known"]
    url: str | None
    observed_at: datetime          # UTC
    detail: str                    # one-line for the renderer

@dataclass
class EmailCandidate:
    address: str                   # lowercased; IDNA-encoded for non-ASCII domains
    sources: list[Source]
    smtp_verdict: Literal["verified", "catch_all", "inconclusive",
                          "invalid", "unprobed"] = "unprobed"
    employer_match: bool = False   # domain ∈ employer.domains
    is_personal_provider: bool = False  # @gmail / @yahoo / @icloud / ...
    # Three-field decomposition (post-dual-voice review). None = abstain.
    belongs_to_person: float | None = None    # 0-1: this address is actually this person's
    current_work_address: float | None = None # 0-1: this is their current work email
    deliverable: float | None = None          # 0-1: a message sent here will land
    score_reasons: list[str] = field(default_factory=list)

@dataclass
class Employer:
    name: str
    domains: list[str]
    since: str | None              # ISO date if known
    until: str | None = None

@dataclass
class Person:
    name: str
    name_variants: list[str]
    handles: dict[str, str]        # {"github": "steipete", "x": "steipete"}
    personal_domains: list[str]
    employer: Employer | None
    former_employers: list[Employer]
    channel_hints: dict[str, Any]  # {"x_dms_open": True, ...}
    # Three explicit states (post-dual-voice review). `single_plausible_match`
    # means "we found one candidate" — NOT "this is definitively the only
    # person." That distinction is what `unique` used to obscure.
    ambiguity: Literal["single_plausible_match",
                       "multiple_plausible_matches",
                       "insufficient_identity_evidence"]
    ambiguity_candidates: list["Person"] = field(default_factory=list)
    # Identity anchors that independently bind this Person. A handle from
    # --person-plan is an untrusted hint until ≥2 anchors bind (Codex #5).
    bound_anchors: list[tuple[str, str]] = field(default_factory=list)
```
### Wire format: `--person-plan`
JSON projection of `Person` plus a `query_hints` block. Host model produces it; `snoop.py` consumes it; `person_resolve.py` independently re-derives the same fields and surfaces deltas (defense against host hallucination).

Example:

```json
{
  "name": "Peter Steinberger",
  "name_variants": ["Peter Steinberger", "Pete Steinberger"],
  "handles": {"github": "steipete", "x": "steipete"},
  "personal_domains": ["steipete.com"],
  "employer": {"name": "OpenAI", "domains": ["openai.com"], "since": "2025-09"},
  "former_employers": [
    {"name": "PSPDFKit", "domains": ["pspdfkit.com"], "until": "2023"}
  ],
  "channel_hints": {"x_dms_open": true}
}
```

Any field can be `null` if the model doesn't know. The resolver's re-derivation closes gaps and flags conflicts.
### Pipeline
```
parse args / read --person-plan
        ↓
person_resolve  (cross-check the plan; surface deltas)
        ↓
fan-out (ThreadPoolExecutor, max_workers=8):
   git_emails | gh_profile | hn_profile | whois_emails | personal_site
     | package_registry | pgp_keyserver | pattern_gen
     | [linkedin_cookies] | [x_bio]
        ↓
cluster (dedupe by lower(address); merge source lists)
        ↓
score  (pre-SMTP, provenance-weighted)
        ↓
verify_smtp top-K work candidates  (skip personal-provider domains)
        ↓
re-score (fuse pre-SMTP with smtp verdict)
        ↓
store.upsert  (SQLite, freshness timestamps)
        ↓
render  (markdown table OR html person card)
```

Three structural moves: the verifier moves from front-of-funnel to end-of-funnel; pattern generation is _one of five_ resolvers rather than the engine; SMTP only runs on top-K work candidates, never on personal-provider addresses where the probe is useless.

**Endpoints.** Two-pass to cover both frequent and infrequent pushers:

1. `GET /users/{h}/events` (`--paginate`). Public push events over the last 90 days, capped at API tier.
  
2. `GET /users/{h}/repos` (`--paginate`), then for each `GET /repos/{owner}/{repo}/commits?author={h}&per_page=1`. Catches users who push once a quarter.
  

**Auth.** `gh` CLI gives 5000 req/hr. Unauthed `api.github.com` gives 60 req/hr (enough for one lookup, not enough for any retry). Prefer `gh`; fall back if missing; surface the path in `diagnose`.

**Latency.** 200ms - 2s depending on repo count. **Cost.** Free. **Hit rate (informal estimate).** 60-70% on developer targets; near-zero on non-developers.

**Critical noise filtering:**

```python
_NOISE_DOMAINS = ("users.noreply.github.com", "example.com",
                  "localhost", "local")
_NOISE_LOCALPARTS = ("noreply", "no-reply")
_BOT_MARKERS = ("[bot]", "dependabot", "github-actions", "renovate")

def _is_noise_email(email: str) -> bool:
    if "@" not in email:
        return True
    local, domain = email.rsplit("@", 1)
    return (
        any(domain.endswith(d) for d in _NOISE_DOMAINS)
        or any(local.startswith(lp) for lp in _NOISE_LOCALPARTS)
        or any(m in email for m in _BOT_MARKERS)
    )
```

**Top failure mode.** Privacy-conscious users set `git config user.email <id>@users.noreply.github.com`. Roughly 25-30% of active GitHub accounts. For those targets `git_emails` returns empty. Surface this explicitly in render output: `"No commit emails (user uses GitHub privacy noreply)"`. The absence should not silently read as "no signal worth surfacing."

**Edge case.** Multi-account devs commit work as `pete@openai.com` (work fork pushed publicly) and personal projects as `steipete@gmail.com`. Don't merge — the domain disambiguates intent, and the renderer's Work/Personal split surfaces both correctly.
### `gh_profile` — explicit display email + bio + profile README (NEW per c2)
Distinct from `git_emails`. That source mines what the user _used to commit_; this one reads what they _publish as their identity_.

**Endpoints:**

- `gh api /users/{handle}` returns `email`, `bio`, `blog`, `company`, `twitter_username` fields. ~20-30% of users set `email` publicly. Free, instant.
  
- `https://raw.githubusercontent.com/{handle}/{handle}/main/README.md` (or `master`). Many devs use the profile-README pattern: "📫 reach me at: [x@y.com](mailto:x@y.com)". Parse with the same email regex used in `personal_site`. ~10-15% extra recall on top of the `email` field.
  

**Latency.** <500ms total. **Cost.** Free with `gh`. **Hit rate.** 25-35% on developer targets (profile email OR profile README); ~5% on non-developers.

**Signal quality.** Very high when present. The user explicitly put it there as their public contact. Profile email gets `Source(type="gh_profile", detail="public profile email")`; README hits get `Source(type="gh_readme", detail="contact line in profile README")`.

**Edge case.** Some profile READMEs hide email behind base64 or image (`![](https://...email-as-png.png)`). Don't OCR. Skip.
### `hn_profile` — Hacker News public profile (NEW per c2)
**Endpoint.** `https://news.ycombinator.com/user?id={handle}`. Plain HTML, ~3KB. Parse the `<tr>` row labeled `email:`.

**Latency.** <300ms. **Cost.** Free. **Hit rate.** ~40% on YC/tech-founder targets (HN users self-select for tech-publicness); near-zero outside that population.

**Resolution dependency.** Need the person's HN handle. The same name+company resolver pass that produces GitHub handles should produce HN handles when applicable. For obscure HN handles, `https://hn.algolia.com/api/v1/search?query="{name}"` filtered to story authors gives high-precision candidates.

**Signal quality.** Very high. User explicitly published. Almost always a current address (HN profiles change rarely).

**Audience.** This source is disproportionately useful for the founder/investor/journalism intent. Not useful for, say, finding a marketing manager's email.
### `personal_site` — scrape declared personal domains + Substack (NEW per c3)
**Endpoints:**

- For each `domain` in `person.personal_domains`:
  
  - `https://{domain}/`, `/about`, `/contact`, `/colophon`, `/imprint`
    
  - Footer extraction on the homepage
    
- Substack pattern: `https://{slug}.substack.com/api/v1/publication` (JSON; author email surfaces in publication metadata when set public).
  
- Look for `mailto:` anchors first (highest precision; semantic). Fall back to regex `[a-z0-9._+-]+@[a-z0-9.-]+\.[a-z]{2,}` on visible text.
  

**Filter:** drop `noreply@*`, `*-bounces@*`, `do-not-reply@*`, `webmaster@*`, `info@*`, `hello@*` (rarely the actual person), and any address whose local-part matches the site's domain stem (e.g. `contact@acme.com` on `acme.com` — probably a generic inbox, not the person's).

**Latency.** 1-3s per domain (HTML fetch + parse). Run in parallel with other resolvers via the ThreadPoolExecutor. **Cost.** Free. **Hit rate.** ~30-50% when `personal_domains` is non-empty. Many writers/devs put contact info on `/about`. Substack hit rate ~60% when the target has a publication.

**Signal quality.** High. Self-published, intentional.
### `package_registry` — npm + PyPI publisher emails (NEW per c2)
**Endpoints:**

- npm: `https://registry.npmjs.org/-/user/org.couchdb.user:{handle}` returns publisher email. Public, required for publishing.
  
- PyPI: `https://pypi.org/user/{handle}/` HTML; less exposed but some users display contact.
  

**Latency.** <500ms each. **Cost.** Free. **Hit rate.** Near 100% on npm publishers (the question is whether the target IS one — ~5-10% of dev targets); ~30% on PyPI publishers.

**Signal quality.** High when present. Publishers self-identify with a real address (npm requires verified email).

**Audience.** Narrow but high-precision. Worth running because the resolver is one HTTP call.
### `x_bio` — X profile bio email regex (NEW per c2)
**Endpoint.** Depends on X auth path. If the user has Bird cookies (`AUTH_TOKEN` + `CT0`) per the last30days pattern, query the profile via the bundled Bird client and parse the bio field. Otherwise via xAI API (paid) or skip.

**Hit rate.** ~10-15% on X-active targets. Some put email in bio for press/business contact.

**Signal quality.** Medium. Self-published but often a press/PR alias, not a personal address.

**Status.** P2 if Bird cookies path is already wired up; otherwise P3 (the wiring cost dominates the source value).
### `whois_emails`
**Endpoint.** `whois <domain>` shell call. Parse for `Registrant Email:` / `Tech Email:` / `Admin Email:` lines.

**Hit rate.** <20% in 2026. GDPR + ICANN redaction is the default for most TLDs. `.com`/`.net` registered before 2018 sometimes still leak. When it does hit, the address is high-trust: the domain owner has admin-channel reasons to read it.

**Critical filter.** Privacy proxies must be detected and dropped:

Without this filter WHOIS is a high-confidence noise pipeline.
### `pgp_keyserver`
**Endpoint.** `keys.openpgp.org` Hagrid. `/vks/v1/by-email/{e}` returns 404 or armored key. There is no documented name-search HTTPS API; HTML scrape of `https://keys.openpgp.org/search?q={query}` works but is fragile.

**Hit rate.** 5-10% of dev targets; near-zero for non-devs. Tech-Reddit-active devs maybe 15%. Trend is downward — corporate IT is killing PGP.

**Signal quality.** Very high when present (cryptographic claim on the UID).

**Verdict.** P3. Long-tail. Consider sunsetting by 2027.
### `pattern_gen` (extraction)
Move `_templates`, `infer_patterns`, `predict`, `rank_candidates` out of `verify_email.py` into `lib/pattern_gen.py`. Signature: `(Person, manual_known: list[(email, name)]) -> list[EmailCandidate]` where each candidate carries `Source(type="pattern", detail="matches company format from N knowns")`. Pattern candidates are guesses; the scorer caps their max score at 0.5 absent corroboration from another source.
### `linkedin_cookies` (opt-in, P3, ToS-edgy)
**Endpoint.** `https://www.linkedin.com/voyager/api/identity/profiles/{public_id}/profileContactInfo`. The LinkedIn mobile app's internal API. Returns `emailAddress` for ~20-30% of profiles (most users hide it behind connection-required gates).

**Auth.** Read `li_at` from the user's Chrome cookie store via the `chrome_cookies.py` pattern from `last30days-skill`. Uses the user's own logged-in session.

**ToS posture.** This is the dual-use red zone. Three guardrails non-negotiable:

1. Explicit per-invocation `--allow-linkedin` flag. Never auto-enable.
  
2. One request per session, human-paced.
  
3. Refuse list input. Single target only.
  

**Recommendation.** Ship last if at all. The capability is real but the ethical/legal posture is the thing most likely to attract attention or get the skill removed from public marketplaces. Document the posture in `SKILL.md` prominently.
### `verify_smtp` (demoted from primary path)
Two changes to the existing engine:

1. **Skip personal-provider domains.** SMTP probing `@gmail.com`, `@yahoo.com`, `@icloud.com`, `@outlook.com`, `@hotmail.com`, `@protonmail.com` is useless (mass-market providers either block RCPT, return greylist 451, or just blackhole the connection) and tips spam filters. Filter at top of `run_batch`.
  
2. **Treat** `inconclusive` **as zero information (revised per c1).** SMTP `inconclusive` on Google/M365 tells us nothing about whether the mailbox exists. The verdict does not justify boosting _or_ floor-ing the score in either direction. The pre-SMTP score from the resolver fan-out stands unchanged. (First draft of this plan proposed a 0.5 confidence floor for `inconclusive + non-catch-all + Google`. That was wrong — it conflated _mailbox-exists_ with _mailbox-is-deliverable-if-it-exists_. We have evidence of the latter, none of the former.)
  
3. **Track MX-provider metadata for the renderer only.** The fact that `openai.com` is M365-hosted is useful to _show the user_ (`"SMTP inconclusive (M365 blocks RCPT)"`) so they understand why the score didn't move post-probe. It is not used as a score input.
  
### `score.py` — provenance-aware scorer
Every weight is explainable. No ML, no calibration data, no opacity. Same posture as the current `_VERDICT_BASE` in `verify_email.py:104-111`, broader inputs.

```python
SOURCE_WEIGHTS = {
    "git_commit": 0.55,       # baseline; decays with age (see _age_tag)
    "gh_profile": 0.55,       # explicit public profile email (NEW per c2)
    "gh_readme": 0.45,        # scraped from profile README; lower extraction trust
    "hn_profile": 0.55,       # explicit HN public profile email (NEW per c2)
    "whois": 0.40,            # high when present, rarely present
    "personal_site": 0.50,    # mailto: or scraped from /about (NEW per c3)
    "substack": 0.45,         # author email from publication metadata (NEW)
    "package_registry": 0.50, # npm/PyPI publisher field (NEW per c2)
    "x_bio": 0.45,            # email regex from X bio (NEW per c2)
    "pgp": 0.45,              # cryptographic claim, but rare
    "linkedin": 0.50,         # only when cookies path opened
    "manual_known": 0.65,     # user passed --known; treat as ground truth
    "pattern": 0.15,          # guess; corroboration multiplies
    "smtp": 0.0,              # not a source on its own; modifies
}

def score_candidate(c: EmailCandidate, person: Person) -> tuple[float, list[str]]:
    reasons = []

    # Base: best single source, with age decay for git_commit.
    base = 0.0
    for s in c.sources:
        w = SOURCE_WEIGHTS[s.type]
        if s.type == "git_commit":
            age_days = (datetime.now(UTC) - s.observed_at).days
            w *= max(0.4, 1.0 - age_days / 365)  # 100% fresh, 40% at 1y
        base = max(base, w)
        reasons.append(s.detail + _age_tag(s))

    # Corroboration: each additional non-pattern source adds.
    non_pattern = [s for s in c.sources if s.type != "pattern"]
    if len(non_pattern) > 1:
        base += min(0.20, 0.08 * (len(non_pattern) - 1))
        reasons.append(f"{len(non_pattern)} independent sources")

    # Employer match × likely-active.
    if c.employer_match and any(s.type == "git_commit" for s in c.sources):
        base += 0.10
        reasons.append("current-employer git commit")

    # Former-employer cap.
    if (person.former_employers
        and any(c.address.endswith(d)
                for fe in person.former_employers for d in fe.domains)):
        base = min(base, 0.40)
        reasons.append("former-employer domain - likely inactive")

    # SMTP modifier.
    if c.smtp_verdict == "verified":
        base += 0.10
        reasons.append("SMTP RCPT accepted")
    elif c.smtp_verdict == "invalid":
        base = min(base, 0.10)
        reasons.append("SMTP RCPT rejected")
    elif c.smtp_verdict == "catch_all":
        reasons.append("domain is catch-all (SMTP non-informative)")

    return round(min(1.0, base), 2), reasons
```
## Disambiguation
Two `Matt Smith`s at the same company. The single most common false-positive class for any email finder. Current `/snoop` has zero protection.
### Resolve-time
```python
def resolve_person(name: str, company: str | None) -> Person:
    candidates = []
    for hit in _gh_search_users(name, company):       # GitHub user search
        candidates.append(_partial_person(hit))
    candidates.extend(_web_disambiguate(name, company))  # light web search
    candidates = _merge_by_handle(candidates)

    if len(candidates) == 0:
        return _empty_person(name, company, ambiguity="could_not_resolve")
    if len(candidates) == 1:
        return _flesh_out(candidates[0], ambiguity="unique")
    return Person(name=name, ...,
                  ambiguity="possibly_multiple",
                  ambiguity_candidates=candidates)
```
### Verify-time guard
If `person.ambiguity == "possibly_multiple"`: never emit a single-line "Verified" output. Force the table, with disambiguating signals (middle initial, GitHub handle, role, location) shown per candidate person, not just per candidate email.

```

| matt.smith@acme.com | 0.85 | git-commit 4d ago (msmith-eng/api-svc) |

```

This output prevents the "I emailed the wrong Matt Smith and now both of them are weird about it" failure mode.
## Freshness
Person changed jobs. Old git commits still public. Old address now bounces or routes to "no longer with the company" autoresponder.
### Signals, in order of reliability
1. **LinkedIn current employer** — best signal; cookie-jar gated; only if user opts in.
  
2. **GitHub bio company field** — `gh api /users/{h} | jq .company`. Free. ~50% of devs fill it out.
  
3. **Last 30 commits by domain split** — if 28/30 are `@openai.com` and 2/30 are `@anthropic.com`, the OpenAI address is current and the Anthropic is residual.
  
4. **Conference / podcast bios with dates** — long-tail.
  
### Score modifier
```python
def freshness_modifier(c: EmailCandidate, person: Person) -> float:
    domain = c.address.rsplit("@", 1)[1]
    if person.employer and domain in person.employer.domains:
        return 1.0
    if any(domain in fe.domains for fe in person.former_employers):
        return 0.5    # also capped at 0.40 in score_candidate
    if c.is_personal_provider:
        return 1.0    # personal-channel; tag separately
    return 0.9        # unknown domain; could be vanity (good) or unrelated (bad)
```

When `person.employer` is unknown (resolver failed), surface in render: `"⚠ Could not confirm current employer; freshness uncertain."`

## Adversarial pass
What's wrong with the above. Things to fix before shipping.

1. `gh api` **is load-bearing for S-01.** If the user doesn't have `gh` installed/authed, the highest-yield resolver returns empty and the whole pitch collapses. Mitigation: fall back to unauthed `api.github.com` (60 req/hr is enough for one lookup); promote `snoop diagnose` from P3 to P1 so users see the gap before it bites silently.
  
2. **GitHub** `events` **only covers 90 days of public push events.** Infrequent pushers return nothing. The `/repos` second-pass mitigates but only for repos the target owns; commits to other orgs aren't captured. Realistic recall: ~70% for active OSS devs, ~30% for everyone else with a GitHub account.
  
3. `steipete@gmail.com` **discovery is a strict improvement but it's a personal address.** Most sales/recruiting intent wants the work email. The render splits work/personal correctly, but the raw score still puts gmail on top. Defensible (more evidence), confusing for the "I need the work email" intent. Mitigation: `--intent=work|personal|either` flag changes default sort. `work` is the implicit majority intent.
  
4. **The** `--person-plan` **schema asks the host model to know employer chronology.** It often doesn't, especially for non-public people. The model will hallucinate `since: "2025-09"` when the truth is "I don't know." Mitigation: schema allows `null` everywhere; `person_resolve` re-derives independently and surfaces conflicts (`"Plan says employer 'OpenAI since 2025-09'; GitHub bio says 'Anthropic'. Conflicting; treating both as candidates."`).
  
5. **WHOIS hit rate is realistically <20%.** Don't oversell.
  
6. **PGP keyservers are dying.** Treat as `<10% hit rate`, downward trend. Ship S-09 last; consider removing by 2027.
  
7. **Catch-all detection is itself getting flakier.** Many catch-all MX servers now greylist or rate-limit; the random-localpart sentinel sometimes 451s when a real address would 250. Not a fatal flaw, but a known-issue line.
  
8. **SMTP probing tips spam filters.** Repeated `RCPT TO` probes can land you in MX denylists. Current code reuses one connection per domain (good), but multi-domain runs still look spammy. Mitigation: per-domain daily probe budget; skip probing when budget exhausted; surface "probing disabled, scoring on resolvers only" in render.
  
9. **Store/watchlist surface is marginal user value.** Most invocations are one-shot. The store pays off only for users running `snoop` in recurring CRM-hygiene workflows — small population. Demote `store.py` + `snoop watch` to P3 (was P2 in the first draft).
  
10. **LinkedIn cookie-jar is the ethical edge case.** User's own logged-in session, so technically not a TOS violation in the same way as a scraping bot — but mass use would be. Ship with: explicit `--allow-linkedin` flag, hard one-call-per-invocation cap, refusal of list inputs.

## Failure modes 1. **Wrong person.** Disambiguation handler refuses single-line "Verified" when `ambiguity != "unique"`. 2. **Stale employer email.** Freshness modifier caps former-employer domains at 0.40 confidence. 3. **Catch-all false-positive.** Already handled in `verify_email.py`. Don't regress. 4. **SMTP path degradation.** Demoted from front of funnel. Plan for eventual sunset. 5. **Dual-use / privacy.** Refuse list input (one person per invocation, hard rule). Local `~/.snoop/lookups.jsonl` log. One-line context probe on first install ("sales / recruiting / journalism / personal"). 6. **LinkedIn blowback.** Rate-limit hard, prefer cached snapshots, treat as opt-in P3. 7. **Host model hallucinated person-plan.** `person_resolve` independently re-derives; surfaces deltas. ## Known limits / sunset candidates - **By 2027:** PGP keyserver path likely gone (`<5%` hit rate, downward trend). Remove if no users complain. - **By 2027:** SMTP probing path likely unrunnable without an MX-provider denylist consequence. Plan an "SMTP off; scoring on resolvers only" fallback shape now. - **By 2027:** LinkedIn Voyager endpoint likely changed or sealed off. Cookie-jar path is best-effort, not a contract. ## Open questions for review 1. **Intent default.** Should `--intent=work` be the default (most users want work email) or should the default be `either` (raw confidence-ranked, user decides)? 2. **Disambiguation hard fail vs soft warn.** When `ambiguity="possibly_multiple"` and the user clearly knows which person they mean (e.g., they passed a GitHub handle in the input), do we still force the table? Or do we trust the explicit handle and proceed? 3. **LinkedIn — ship or skip.** Real capability, real ethics edge. Three options:
- Skip entirely. Cleaner posture; lose 20-30% recall on non-developers.
  
- Ship with explicit `--allow-linkedin` flag and hard guardrails. Best capability; some risk.
  
- Ship in the private beta-channel companion repo only (`mvanhorn`-style). Best of both? Or just confusing distribution?
  

4. **Store / watchlist.** Worth the engineering, or marginal? Today the implicit answer is P3 (demoted from P2 in the adversarial pass). Real question: do you actually run `/snoop` recurringly enough for the cache to pay off, or is it a one-shot tool for you?
  
5. `--person-plan` **as the wire format.** Adds complexity for the host model. Worth it for the disambiguation/freshness wins, or is the implicit "model brainstorms, script does its own resolving" path simpler enough to keep?
  
6. **Output-default shape.** Today the SKILL.md says "one-line `Verified` when there's a clear answer; table otherwise." The redesign defaults to the table always (with receipts). Lose the one-liner? Or keep it as `--terse` mode?
